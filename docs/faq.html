FAQ

The questions a reviewer asks.

Including the ones that are least comfortable to answer.

The mechanism

Isn't this just a bridge transfer?

A bridge transfer ends when the money arrives, and by default anyone may be the one to land it. Berth changes who is permitted to complete it and then executes the instruction the bridge deliberately does not run. The transfer is the substrate, not the product.

What actually stops someone else from minting?

A line in Circle's deployed MessageTransmitterV2: require(destinationCaller == msg.sender, "Invalid caller for message"). Berth did not write it, cannot change it, and does not need to be trusted about it. The proof page offers the same message from unrelated addresses and shows the refusal.

Why does hookData need anyone to execute it?

Because Circle says so. Their documentation reads: “CCTP does not implement hook execution in the core protocol. Instead, hooks are treated as opaque metadata.” And in code, TokenMessengerV2._handleReceiveMessage reads the recipient, the token, the amount and the fee, and never reads hookData at all. The instruction crosses and waits for someone.

Why is the mint separate from the hook?

Because they cannot be combined. Batching routes through Multicall3's aggregate3, which forwards each call, so msg.sender becomes Multicall3 and the gate refuses it. We expected to ship atomic delivery and found it unavailable; the proof page reproduces the refusal live. Exclusivity and atomicity are mutually exclusive here.

KeeperHub

What breaks if you remove KeeperHub?

The named caller is a KeeperHub wallet, so with KeeperHub gone no address is permitted to mint and the burned USDC is stranded permanently. That wallet also holds zero native balance on both chains, so without sponsorship the only permitted caller cannot pay for a transaction either. Then the hook never runs. See the removal test.

Couldn't a script with a funded key do the same thing?

A script could burn and mint. It could not be this wallet, and this wallet is what the message names. The gate does not care how capable the caller is; it compares an address. Whoever holds the named address is the only party CCTP will admit, and here that address is custodied and sponsored by KeeperHub.

Which KeeperHub features are actually used?

Sponsored execution through the forwarder, the Turnkey key with its EIP-7702 delegation, the workflow executor API, and the direct execution API's simulate as pre-flight. MCP, CLI, x402 and MPP are not used and therefore not claimed.

Trust and limits

Could whoever holds the private key mint without KeeperHub?

Yes, if the key were exportable. The claim is precise: the permitted caller set has size one, enforced on-chain. It is not a claim about key custody. We looked for a way to prove non-exportability from outside and did not find one, so we do not assert it.

This is testnet. Does it mean anything?

The contracts, addresses and enforcement are the production CCTP V2 deployments; the value is testnet value. A testnet can show the mechanism holds. Only a mainnet burn would put something at stake, and we say so rather than implying otherwise.

Why should I believe the numbers on this site?

Don't. Press the button on the proof page and your browser reads them from public RPCs. Or clone the repository and run npm run verify, which needs no credentials. Then run npm run verify:tamper, which mutates the claims seven ways and requires the verifier to fail on each.

What went wrong while building this?

Two designs we expected to ship turned out to be impossible, and both are documented rather than quietly dropped. We also found that simulate reports wouldRevert: false for a send the wallet cannot pay gas for, and filed it upstream as KeeperHub#2564.
