Mechanism

One gate, enforced by someone else's contract.

Berth contains no Solidity. The rule that makes it work was written and audited by Circle; Berth only decides what to pass into it.

The sequence

1 · burn  Base Sepolia  →  depositForBurnWithHook
    destinationCaller = the KeeperHub wallet  ·  hookData = a real call

2 · attest  Circle  →  signs the message, rewrites only the nonce and executed finality
    the gate and the instruction cross byte-identical, and neither is executed

3 · mint  Ethereum Sepolia  →  receiveMessage
    admitted for one address, refused for every other

4 · hook  Ethereum Sepolia  →  Berth executes the carried instruction

Steps 3 and 4 are two transactions, not one. That is a constraint rather than a choice — see below.

Where KeeperHub is load-bearing

The removal test

The honest question for any sponsored integration is what survives if you delete the sponsor. Here is the answer, step by step.

The named caller is a KeeperHub wallet. It is a Turnkey key delegated via EIP-7702, and it is what destinationCaller points at.
Remove KeeperHub → no address on the destination chain is permitted to mint. The burn already happened. The USDC is stranded permanently.
That wallet holds no native balance. Zero on both chains, verifiably, at all times.
Remove KeeperHub's sponsorship → the only permitted caller cannot pay for a transaction, so it cannot mint even though it alone is allowed to.
The hook runs through the same wallet. The instruction Circle declines to execute is executed by the party that minted.
Remove KeeperHub → the instruction is delivered and never runs.

Without KeeperHub there is no address permitted to mint this USDC. The burn is irreversible; the mint is exclusive.

Which KeeperHub surfaces are used

Only surfaces with a real call site are listed. Anything not used is not claimed.

Sponsored execution
execute(address,address,uint256,bytes) at 0x9aefaff8 on the forwarder. Every one of the five transactions went through it.
Turnkey key + EIP-7702
The acting wallet is a delegated account, 0xef0100…, identical designator on both chains.
Workflow executor API
PATCH /api/workflows/{id} to set exact arguments, then POST /api/workflows/{id}/execute. This path is gas-sponsored.
Direct execution API
POST /api/execute/contract-call with simulate: true as pre-flight before every broadcast.
Not used
MCP, CLI, x402, MPP, agent-authored workflows. No call site, so no claim.

Why there is no contract

Two designs we cannot build

Both are the obvious answer. Both fail, and the second fails for an instructive reason.

A hook executor as mintRecipient. It would receive the mint and run the instruction atomically. It cannot: TokenMessengerV2._handleReceiveMessage mints and never calls back into the recipient, so the contract would take the funds and never execute.

Batching the mint and the hook. One transaction, one signature. It cannot either, and the reason is the gate itself. KeeperHub's batch node routes through Multicall3's aggregate3, which forwards each call — so msg.sender at the transmitter becomes Multicall3 rather than the named caller, and Circle refuses it.

The proof page reproduces that live: the identical call, from the identical wallet, is refused when routed through Multicall3 and admitted when sent directly. Exclusivity and atomicity are mutually exclusive here, and exclusivity is the product.

Shipping no Solidity also keeps contributor-written code out of the value path, and leaves the guarantee resting on an audited contract rather than on a modifier we wrote.
