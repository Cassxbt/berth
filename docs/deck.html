Exclusive cross-chain delivery.

A burn only one address on earth is permitted to complete — and that address is a KeeperHub wallet.

berth-phi.vercel.app

The problem

The window where the money exists nowhere.

A CCTP burn is irreversible the moment it lands. From that block until someone calls receiveMessage on the destination chain, the USDC exists on neither chain.

And by default, any address may be the one to call it.

The default nobody changes

destinationCaller is optional.

// almost every CCTP integration ships this
destinationCaller: bytes32(0)

// which Circle documents as
"or bytes32(0) if message can be received by any address"

The value is committed. Whoever shows up first finishes the job.

One mechanism

Berth names the caller.

depositForBurnWithHook(
  amount, …
  destinationCaller: 0x3db6f359…0cb2 // the KeeperHub wallet
  hookData: transfer(0x…dEaD, 500000) // Circle will not run this
)

Circle states it plainly: “Hook execution is left entirely to the integrator.” In code, _handleReceiveMessage never reads hookData at all.

Who enforces it

We wrote no Solidity.

// MessageTransmitterV2, deployed and audited by Circle
require(
  destinationCaller == msg.sender,
  "Invalid caller for message"
);

We supply the argument. Circle supplies the refusal. There is no contract of ours anywhere in the value path.

The gate, live

Same message. Different caller.

from 0x000000…dEaDInvalid caller for message
from 0xd8dA6BF2…6045Invalid caller for message
from every other address on earthInvalid caller for message
from 0x3db6f359…0cb2 — the KeeperHub walletadmitted

Reproducible by anyone with a public RPC. No wallet, no key, no gas.

Why KeeperHub is load-bearing

Two locks, not one.

One. The only address permitted to mint is a KeeperHub-custodied wallet. Remove KeeperHub and the burn is irreversible with nobody able to complete it.

Two. That wallet holds 0 native ETH on both chains. It is the only address allowed to mint and it cannot pay for a transaction without KeeperHub's sponsorship.

Without KeeperHub there is no address permitted to mint this USDC.

The instruction Circle would not run

Carried by Circle. Executed by Berth.

The second transfer packed transfer(0x…dEaD, 500000) into hookData. Circle delivered it byte-identical and executed none of it — exactly as documented.

Berth minted as the only permitted caller, then ran the instruction. The named recipient received exactly 500000.

A constraint we found, not assumed

Exclusivity and atomicity are mutually exclusive.

We expected to deliver mint-and-hook in one transaction. We cannot. KeeperHub's batch path routes through Multicall3's aggregate3, which forwards each call — so msg.sender becomes Multicall3 and the gate refuses it.

direct    → admitted
batched   → Invalid caller for message

Same call, same wallet. The gate is real enough to break our own design.

Do not trust us

Verify every claim yourself.

$ npm run verify
  24 ok   0 FAILED  no wallet, no key, no credentials

$ npm run verify:tamper
  7/7 lies detected  the verifier is shown to fail

Both run in CI on every push and daily, because these claims describe live chain state and can go stale without a commit.

What is not true yet

Stated before you ask.

Testnet only, against production CCTP contracts. Gas was always sponsored; the self-funded path is untested.

Exclusivity is about callers, not custody. We did not find a way to prove the key is non-exportable, so we do not claim it.

Hook delivery is two transactions and nothing retries if the second fails. Two transfers is not a corpus, so we claim nothing about throughput.
